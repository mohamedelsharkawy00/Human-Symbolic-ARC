## UPDATE 2026-05-24 (b) -- NEW DSL OP: BidiColorMap[k] (bidirectional swap)   ##
################################################################################
Added an ordinary constant-param op for pure-recolor tasks (e.g. 0d3d703e:
1<->5, 2<->6, 3<->4, 8<->9). NOT a learned table -- the search finds it.

WHY a SWAP and not a directed map: a directed Recolor/MapTo[X->Y] node has one
fixed param and runs identically on every train example, so it can't satisfy a
task that needs 8->9 on one example AND 9->8 on another (0d3d703e pairs 1 vs 3).
A bidirectional swap dissolves that: one node does a->b AND b->a, correct in both
directions with identical program behavior. The puzzle's 4 swaps are also
disjoint, so they compose order-free (no clobber, unlike chained directed maps).
Reach = INVOLUTIONS only (pairwise swaps); a 3-cycle recolor (1->2->3->1) is NOT
expressible. Most ARC recolor tasks are swaps/fixed maps, so this is fine.

SEMANTICS: BidiColorMap[k], annotation k in [0,44] indexes one of the 45 unordered
color pairs {a,b}, 0<=a<b<=9, enumerated row-major (k=0->{0,1}, k=44->{8,9}).
Swaps every pixel of color a<->b across all objects; other colors untouched.
Position-blind, self-inverse. k is the raw node value (get_variant_value default
= idx, so value == k == pair index; renders as [0]..[44]).

WHY it's FINDABLE by the beam (CONFIRMED -- 0d3d703e now solves): a single correct
swap improves the per-example score immediately (it doesn't depend on later nodes
"clicking"), so the beam hill-climbs -- the 4 right swaps survive, the 41 wrong
ones get pruned each step. The depth-survivability fear (correct deep program
pruned early) does NOT bite here because each prefix is also locally best-scoring.
Param space is 45, but most are dead (a swap among colors absent from the puzzle is
useless) -- a future per-puzzle op-mask (3 - Search/Op Masking.md, design-only)
could cut it if 45 ever bloats search on swap-heavy puzzles.

WHERE (all edits #else/portable-safe; ordinary annotated op, NO learned table, NO
context plumbing -- the constant lives in the program node like any other op):
  - environment.hpp: BidiColorMap added to the NODE_PRIMITIVES X-macro, annotated,
    VAR_COUNT 45 (LAST entry). No new puzzle fields, no detector.
  - cuda_dsl.cuh: BidiColorMap added to gpu_op_type enum (LAST -- MUST stay
    parallel to node_type; fixed_dsl.hpp:212 casts node_type->gpu_op_type BY INDEX).
  - cuda_solver.cu: gpu_exec_bidi_color_map() (decodes k->pair, swaps) + dispatch
    case passing `value`. No template/ctx/example-data changes.
The beam generator iterates primitive_types/primitive_count, so it's auto-included.

VERIFIED solution (solutions/0d3d703e.txt, user-confirmed solves):
  Input BidiColorMap[12] BidiColorMap[20] BidiColorMap[24] BidiColorMap[44] Union
  k indexing: [12]={1,5} [20]={2,6} [24]={3,4} [44]={8,9}. Input lays the full
  grid as ONE object; 4 disjoint swaps recolor every cell; Union paints to canvas.
  NOTE on source op: Input is the right choice here, NOT InputObjects. InputObjects
  segments into connected components first, which only reconstructs the full grid
  if the components tile it gap-free; Input is unconditionally correct for a whole-
  grid recolor. (Tried InputObjects first, switched to Input.)
Confirmed working via the user's Windows build. A full EVAL_MODE run is still the
authority for whether this REGRESSED anything else or generalizes to eval recolor
tasks -- do that before submission. If you add/rename core files,
kaggle/input/solver-source-code/ is 100% regenerated by scripts/kaggle_push.py --

## UPDATE 2026-05-24 -- DSL solver changes: Union canvas-op + Extend rays-only ##
################################################################################
The DSL has TWO "set" op families (all impl in src/cuda_solver.cu only;
cuda_dsl.cuh + environment.hpp just declare the enum -- no CPU mirror):
  1. CANVAS-set: Union(∪), Intersection(∩), Difference(−). Contract = "write-only
     on ctx.output canvas, pass src through UNCHANGED." They paint/clear canvas
     pixels but must NOT modify the object list (a downstream per-object op like
     ExtendOrthogonal must still see each object separately).
  2. LIST-set: UnionL, IntersectL. These DO collapse N objects -> 1. That's THEIR
     job. (UnionL = world-coord overlay, last-wins; IntersectL = top-left-aligned
     shape ∩.) Both commutative (order-independent).

FIX: gpu_exec_union previously VIOLATED the canvas contract -- when src.count>1 it
merged all objects into one and returned that. Now it passes src through like
Intersection/Difference. Build verified OK 2026-05-24 (user).

Of 15 Union solutions, 14 were safe (terminal Union, or Union-before-a-source-op).
0ca9ddb6 was the one behavior-changing case; it has since been rewritten by hand
(see the Extend block below) and no longer depends on the old merge behavior.

DSL: Extend ops now RAYS-ONLY (solver change, 2026-05-24). gpu_exec_extend_
orthogonal / gpu_exec_extend_diagonal previously output (seed/body pixels + rays);
now they emit ONLY the rays. A single-pixel seed contributes NO cell of its own.
Callers that need the originals must re-stamp them (lay them on the canvas).
  - 0ca9ddb6 (hand soln): REWRITTEN for rays-only and works (user-confirmed). New
    shape lays the originals FIRST, then paints recolored halos on top:
      InputObjects -> Union
      -> InputObjects -> Filter[1] -> ExtendOrthogonal[1] -> Recolor[7] -> Union
      -> InputObjects -> Filter[2] -> ExtendDiagonal[1]  -> Recolor[4] -> Union
    12 nodes. (Recolor no longer clobbers seeds since rays-only excludes them.)
  - 0962bcdd (hand soln): FIXED by the user for rays-only (its center cell had
    come only from the diagonal Extend's seed).
  - radius 0 now yields EMPTY output (was body-only). No current soln uses [0].
  Both hand solutions are believed-correct; a full EVAL_MODE run is still the
  authority before submission (also confirms no OTHER soln regressed).

DSL human-likeness note (context for future expressivity work): hand solutions run
~10-13 nodes for tasks a human does in 2-3 mental steps. The gap is structural DSL
tax, not redundancy: (a) source ops reset `last`, so perception (InputObjects) is
re-fetched per branch -- no object reuse without a Save/Load slot; (b) Extend can't
take a target color, so each halo needs a separate Recolor; (c) no per-color map,
so each color is an unrolled branch. Two cheap levers to shrink programs toward
human depth: a color param on Extend (folds Recolor) and a Save/Load slot (reuses
perceived objects). Neither done; both are additive (won't break existing solns).

6b. 4-GPU PARALLELISM (L4 x4) -- IMPLEMENTED + PROVEN
================================================================================
Runs 4 solver processes, one per L4, each on a contiguous shard; merges outputs.
VERIFIED on the full run: 4 distinct GPUs (bus 03/04/05/06), shards [0,60)
[60,120) [120,180) [180,240), merged to 240 tasks, 0 missing/dupes/extras.

GPU steering (ZERO CUDA code changes, confirmed live):
- Each child process gets CUDA_VISIBLE_DEVICES=N (set in subprocess.Popen env
  BEFORE start). It sees its assigned L4 as device 0; cuda_solver.cu uses the
  default device, so no clash. The [GPU] ... bus XXXX line printed by cuda_init()
  shows distinct bus IDs per shard = proof of 4 separate GPUs.

Solver side (DONE, in main.cpp headless config):
- ARC_SHARD_INDEX (0..N-1) + ARC_SHARD_TOTAL (e.g. 4). CONTIGUOUS sharding:
  chunk = ceil(total/shards); shard solves [shard*chunk, +chunk). Sets the
  solver's start puzzle_idx + reload + caps benchmark_puzzle_limit to the shard
  count. Each writes submission_<shard>.json (single-shard -> submission.json).
- ARC_PUZZLE_LIMIT still works as an overall cap (0 = all 240).

Notebook side (DONE, kaggle_ref/arc_build/build.py):
- Compile once. Launch SHARDS Popen with CUDA_VISIBLE_DEVICES=s + shard env, each
  logging to shard_<s>.log. Wait all. Merge submission_0..3.json (dict update,
  dupe-check) -> /kaggle/working/submission.json. Verify all task_ids present.
- Knobs at top of the run section: SHARDS, PUZZLE_LIMIT ("0"=all), TIMEOUT
  (seconds/puzzle), and EVAL_MODE (top of file). Adjust per run.

Why no race: 4 separate PROCESSES (not threads), disjoint task ranges, separate
output files, merge runs only after all p.wait(). Nothing shared to race over.
Output order is irrelevant (submission.json is a dict keyed by task_id).

6c. FIRST SUBMISSION SCORING ERROR (2026-05-22) -- ROOT-CAUSED + FIXED
================================================================================
The first submission (v15, full 4xL4 run) FAILED with "Submission Scoring Error"
-- NOT a low score, an invalid-output rejection. The run itself was perfect:
4 distinct GPUs (bus 03-06), 240/240 tasks, clean merge, ~3h09m.

ROOT CAUSE: predicted grids contained -1 cell values. ARC cells must be int 0-9.
The solver uses -1 as an internal sentinel (transparent/uncomputed) and it leaked
into real predicted grids; submission.hpp dumped them raw -> scorer rejected.
(Seen in the log sample entry: [[3,2,...,-1],[8,7,8,-1,-1,-1],...].)

FIX: submission.hpp grid_to_json now clamps any cell <0 or >9 to 0. Also build.py
now VALIDATES the merged submission.json (all cells 0-9, rectangular) and prints
"bad cells / bad shapes" + a ">>> COMPLETE + VALID ... Safe to submit" gate.
NEXT RUN: confirm "VALIDATION: bad cells: 0 | bad shapes: 0" before submitting.

ALSO CONFIRMED HERE: the 4-shard run partially QUEUED -- shards 0,1 finished at
6422s/7142s but shards 2,3 at 11340s (~3h09m total). ROOT CAUSE (user-confirmed):
SELF-CONTENTION from two concurrent runs on one account. A submission triggers a
SCORING RERUN that runs CONCURRENTLY with your manual commit run -- both draw from
your 4-GPU pool, so 8 shard-processes fight over 4 GPUs -> each run gets ~2 ->
shards 2,3 queue. (User stopped the manual run; the competition scoring rerun
kept going independently -- proving they're separate concurrent executions. This
is the forum's "double GPU quota consumption".)
  CORRECTION (user only pressed Submit, never manually committed): Submit ITSELF
  auto-spawns TWO runs -- an auto-commit run (on the placeholder data) AND the
  scoring rerun (on the hidden set) -- both under your account, both drawing from
  your 4-GPU pool. So a single Submit click = 8 shard-processes over 4 GPUs ->
  shards 2,3 queue -> the ~3h slowness. This is a KNOWN Kaggle behavior
  ("double GPU quota"); there is a veteran workaround notebook
  (mhviraf/example-of-how-to-avoid-your-kernel-running-twice) whose trick is:
  write a dummy submission immediately, then DELIBERATELY crash (`[].shape`) if
  the test set is the small placeholder, so the expensive solve only runs on the
  big hidden set. That size-discriminator does NOT work for ARC (placeholder and
  hidden are BOTH 240 tasks).

  *** THE CLEAN FIX (recommended, not yet implemented): gate on run type ***
  The probe showed env var KAGGLE_KERNEL_RUN_TYPE exists. Plan:
    - At notebook start, always write a VALID dummy submission.json (instant:
      all-zero grids for every task_id) so the commit run "succeeds" fast and
      frees its GPUs immediately (no contention).
    - Read KAGGLE_KERNEL_RUN_TYPE; PRINT it (we still need to learn its exact
      value in a real scoring rerun -- likely "Interactive"/"Batch" for commit
      vs something else for the rerun). Only when it's the scoring-rerun value,
      do the full 4-GPU ~2h solve and overwrite submission.json.
    - Net: commit run = seconds, scoring rerun = all 4 L4s uncontested, full
      speed, no 2x contention, no manual babysitting.
  FIRST submission with this gate must PRINT the run-type value so we confirm the
  exact string, then harden the equality check.

  INTERIM workarounds if not gating yet: (a) press Submit, then in the browser
  STOP the auto-commit run so the scoring rerun gets all 4 GPUs (user-confirmed:
  stopping the commit run does NOT stop the scoring rerun -- they're independent);
  (b) single-process submission (proven ~1h50m, no shard queue at all).
